# ESP32嵌入式终端通信与OTA升级系统：面试讲解

整理日期：2026-10-14。面向 MCU / RTOS 固件岗位。
按能独立解释和复现的内容选用简历表述；数值应对应实际记录的时间、固件与场景。

## 一分钟项目介绍

项目由两块 ESP32 与 STM32F407（ARM Cortex-M4）组成。A 板采集温湿度和距离，通过 TCP 向 B 板发送数据；B 板是通信网关，接收传感器数据、与 STM32 双向通信，并通过 MQTT TLS 接入 ThingsBoard。STM32 采集摇杆、处理按键，在 OLED 同屏显示传感器与摇杆状态。

B 板从 Arduino 迁移到固定 ESP-IDF v6.1，使用 FreeRTOS 独立处理 UART、网络、云端、心跳和按键。通信采用带 CRC 的二进制帧与流式解析，结合 ACK、重试、去重和会话握手，支持单板重启后的恢复。云端支持远程阈值配置与 NVS 保存。本地网页 OTA 使用两个应用分区，新版本先做启动检查，失败自动回滚。

本轮继续把 STM32 USART2 接收升级为 DMA 循环缓冲与 IDLE/HT/TC 通知，并增加接收统计和任务资源观测。DMA 的验收数字见同目录 UART_DMA_SUMMARY.json。

## 五分钟讲解顺序

1. 先说明三块板的职责，以及 GPIO16/17 与 STM32 PA2/PA3 的双向 UART 接线。OLED 位于 STM32；B 板通过 UART 回传 A 板数据。
2. 解释帧格式：AA55、版本、类型、32 位序号、长度、负载、CRC-16/CCITT-FALSE，字段使用大端。帧长有上限，接收字节进入流式解析器。
3. 解释任务所有权：STM32 TaskB 独占 USART2 和解析器；TaskA 通过短保护区读取传感器快照，摇杆共享数据使用互斥锁。B 的 UART 和 socket 各由所属任务管理，其他任务读取快照。
4. 展开一个可靠性案例：单板重启后如何建立新会话，或 MQTT 状态变化如何与 worker 的初始化顺序配合。
5. 说明 OTA 生效条件及失败回滚，再展示 DMA 接收和资源观测的实际记录。

## 案例一：单板重启与会话恢复

### 问题与依据

原代码审查发现：仅使用序号去重时，STM32 重启会把序号恢复为 1，而 B 保留旧序号，可能确认数据却不更新业务快照。这是从原实现推导的风险，不能说成已经在原固件上完成了故障复现。

### 方案

用 REQUEST → OFFER → CONFIRM → ACK 建立会话。B 分配 64 位会话号，确认成功后才清理对应去重状态；重复确认不重置已收到的数据。数据和 ACK 同时匹配会话、类型与序号。B 重启后拒绝旧会话，STM32 重新握手。

### 实测证据

2026-10-13 阶段 3 已实际验证两端分别重启后的恢复；记录在 STEP3_STATUS.md。确认会话到首帧的 6ms 是局部间隔，不是复位总耗时。
本轮 DMA 固件的 STM32 单独复位记录在 UART_DMA_STATUS.md 与 logs/dma-stm32-reset-*。B 保持运行，新会话建立后序号重新从 1 发送。

### 面试追问

- 重复帧为什么还要 ACK？发送端可能只是丢了 ACK。
- 为什么不能把会话号直接当认证？它用于区分重启后的通信状态，没有提供安全认证。
- 序号环绕如何判断新旧？使用无符号差值及半范围判断，避免普通大小比较失效。

## 案例二：MQTT 连接状态与订阅初始化

### 现象

B 的早期云端版本先遇到时钟未就绪，随后遇到连接建立却提前被关闭。历史联调在 B 工程 CLOUD_STATUS.md 中分别记录为 0.6.2、0.6.3、0.6.4。

### 定位与根因

检查 clock_ready、MQTT CONNECTED、订阅初始化、SUBACK 和 worker 超时判断的先后关系。CONNECTED 回调可能在 worker 等待接收队列时到达；worker 返回后若直接按旧的订阅状态判断，就会提前关闭新连接。

### 修改与验证

先初始化当前连接的订阅状态，再判断本次连接的超时；所有 SUBACK 完成后才请求共享属性和发送遥测。保持证书与主机名验证，等待 SNTP 获得有效时间。历史 0.6.4 联调记录包含遥测/PUBACK、重启后恢复，以及 60 秒周期保存。
描述结果时区分“已自动恢复”和“没有任何网络错误”；本轮 OTA 后也出现过一次 TLS 建连失败，自动重试后恢复。

### 面试追问

- MQTT 回调为什么先排队、由任务解析 JSON？控制回调耗时，把 NVS 与业务处理放在明确的任务上下文。
- 为什么等待 PUBACK？确认 QoS 1 消息已获得协议层确认。
- 断网时是否保存历史？当前设计恢复后上传最新快照；离线历史补传尚未实现。

## 案例三：OTA 启动检查与回滚

### 设计

先写未运行的应用分区，检查芯片、工程名、长度、SHA-256 和镜像格式。全部通过后才选择下一次启动分区。新程序处于 PENDING_VERIFY，通过协议自测、关键任务存活和堆检查后才标记 VALID。

### 实测

2026-10-14 实际网页完成 0.7.0 → 0.7.1；约 20.850 秒启动检查通过。上传单独构建的 0.7.2-check，约 10.760 秒主动注入健康失败，设备自动回到 0.7.1。错误口令、SHA-256 不匹配和中途停止上传也已验证原程序继续运行。
完整证据在 B 工程 STEP7_STATUS.md、STEP7_SUMMARY.json。诊断失败是软件主动注入，未进行物理断电故障验收。

### 面试追问

- 为什么先确认任务健康再标记 VALID？提前确认会失去启动失败回滚的保护。
- CRC、SHA-256 和数字签名分别解决什么？CRC 检测协议字节错误；SHA-256 检测文件一致性；数字签名验证发布者与内容真实性。本项目尚未配置固件签名。
- 阈值为什么没有丢？NVS 位于独立分区，升级应用时没有擦除；实际回滚后仍读到 revision=8。

## 本轮新增：DMA 的讲解要点

- STM32F407 USART2_RX 使用 DMA1 Stream5 / Channel4，循环模式；256 字节 DMA 区、512 字节软件 FIFO。
- IDLE、HT、TC 只用于通知接收进度，完整帧仍由 CRC、长度和流式解析器判定。
- UART 和 DMA IRQ 优先级同为 6，避免两个生产者回调嵌套修改接收游标。
- 回调从当前 NDTR 计算写入位置，避免把延迟到达的旧 HT Size 当成新数据。
- 短 ISR 把新增字节复制到 FIFO；TaskB 完成协议处理。错误回调记录状态，TaskB 负责中止、清理、重启接收。
- 需要在 DMA 覆盖未处理数据之前响应 HT/TC，FIFO 也有容量上限。CRC/重试不能替代及时排空缓冲。
- 剩余栈空间是本次执行路径下的水位；接收事件减少不等于已经测得同等比例的 CPU 使用率降低。
